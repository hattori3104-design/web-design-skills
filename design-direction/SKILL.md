# Design Direction Skill

記入済みヒアリングシートを入力に、デザイン方向性提案書（HTML下書き）を生成する。
思想は **半自動**：機械的に埋める部分と、デザイナーの判断が要る部分を明確に分け、後者は「案」または「要確認」として残す。

**必ず守る原則**
- 出力前に `branding-strategy` スキルの `references/branding-knowledge.md` を読み、WHY→HOW→WHATの論理と失敗例の知見を反映する。
  - **フォールバック**：同ファイルが存在しない場合（2026-07-05棚卸し時点で欠落）、`branding-strategy/SKILL.md` 本文の要点（BtoB=知覚リスク／BtoC=自己一致性、ゴールデンサークル、失敗例3つ）で代替し、詳細数値は引用しない。欠落した旨を出力冒頭で一度伝える。
- コンセプトは**断定せず2〜3案**出す。配色のhex・フォントは**候補**として出す。
- 出力末尾に**「人が確認すべき箇所」チェックリスト**を必ず付ける。

## Step 1: 入力シートを読む

**シートの置き場所**：白紙の雛形は `claude-project/テンプレート/Webヒアリングシート.xlsx`（2026-08-07に `web-design-skills/examples/` から移設）。案件で使うときは雛形を複製し、記入済みのものは案件フォルダの `01_ヒアリング` に置く。**雛形そのものは編集しない。**

ヒアリングシートの形式に応じて読み込む。

- **Googleスプレッドシート**：`Google Drive:read_file_content`（fileId指定）。
- **xlsx**：`extract-text file.xlsx` または pandas で全シートを読む。改善版は3シート構成（「ヒアリングシート」「トーン診断」「記入ガイド」）。**トーン診断シートの○の位置を必ず拾う**。
- 記入が薄い・空欄が多い場合は、その項目を「未記入（要ヒアリング）」として扱い、勝手に創作で埋めない。

読み取る主な対応（改善版シートの設問番号・**2026-08-07に全48問へ改訂**）：

| 提案書セクション | 参照する設問 |
|---|---|
| 0. ゴール | Q9–11（＋**Q13** リニューアル時の現状の数字） |
| 1. ターゲットと不安 | Q18–22 |
| 2. コンセプト（WHY） | **Q14–17**（今どう思われているか／どう思われたいか／価値・想い／人に例えると） |
| 3. トーン&マナー | **トーン診断シート** ＋ **Q37**（見た人にどうなってほしいか）＋ Q38 |
| 4. 配色 | Q39（＋Q15の印象） |
| 5. フォント | Q40（明朝/ゴシック寄り） |
| 6. 参考サイト | Q26–29 |
| 7. 変えない/変える | **Q42**（リニューアル時）＋ Q12 |
| 8. 次のステップ | Q43–44 |
| （全体の前提）素材の制約 | **Q30–33**（ロゴ形式／写真の有無／販促物／今の文章・写真を変えてよいか） |

> 番号が変わっているシート（2026-08-07以前の旧42問版）を渡された場合は、番号ではなく**設問の文言**で対応づける。旧版には Q13（現状の数字）・Q14（今どう思われているか）・Q37（見た人にどうなってほしいか）・素材の選択式設問が存在しないため、それらは「未記入（要ヒアリング）」として扱う。

## Step 2: 内部で方向性を組み立てる（出力前の思考）

`branding-knowledge.md` を踏まえ、頭の中で次を済ませてから書き始める。

1. **BtoB / BtoC 判定**（Q5）。BtoB＝知覚リスク極小化・QCDF・実績の可視化を軸に。BtoC＝自己一致性（Q22「こうありたい姿」）を軸に。
2. **コンセプト案を2〜3**。Q15–17を素材に、ゴールデンサークルのWHYを一言に昇華する。各案に「狙い」を1行添える。断定しない。
   - **Q14（今どう思われているか）とQ15（どう思われたいか）の差を必ず見る。** この2つのギャップが、デザインで埋めるべき距離そのもの。提案書のコンセプト章では「今こう見えている → こう見せたい」という形で出発点を示すと、なぜこの方向にするのかが伝わりやすい。Q14が空なら「要確認：現状の印象」と書き、理想だけで組み立てない。
3. **トーンの言語化**。トーン診断シート（7軸）の○位置を、提案書テンプレの4軸トラックに集約して反映する。
   - **Q37（見た人にどうなってほしいか）を最優先の手がかりにする。** 「かわいい」「かっこいい」のような形容詞は人によって想像するものが違うため、クライアントが挙げた形容詞よりも、Q37に書かれた「見た人の気持ち・行動」のほうを判断の軸に据える。トーン診断の○位置とQ37が食い違う場合は、どちらを採るかを決めつけず、提案書に「ここは確認したい」と残す。
   - **集約基準**：テンプレの4軸は診断の軸1〜4（堅実⇔革新／上品⇔親しみ／余白⇔情報量／無機質⇔手触り）をそのまま使う。残る軸5〜7（高級⇔身近／誠実⇔遊び心／力強い⇔やわらか）はトラック表示せず、コンセプト・配色・写真の判断材料として内部で使う。ただし案件で軸5〜7のどれかが極端（1または5）で方向を強く規定する場合は、近い4軸の1つと差し替えてよい。
   - **位置の%変換**：○位置 pos(1〜5) を `left` に変換する。目安は pos1→12% / 2→28% / 3→50% / 4→72% / 5→88%（端の見切れ防止のため0〜100%でなく12〜88%に寄せる）。
   - 4軸の○から、目指す形容詞3つ・目指さない形容詞を1行で言語化する。
4. **配色・フォントは候補**。「信頼を示すなら紺系（例 #1B3A5B 前後）」のように、方向＋例示hexを出す。確定でないと明示。
   - **2026年のトレンド方向（引き出しの一つとして）**：トーン診断の結果と相性が良ければ、次の8方向も候補に加えてよい。断定はせず、あくまで選択肢の一つとして提示する。
     - レトロフューチャリズム調：懐かしさ×今っぽい質感の組み合わせ。エンタメ・Z世代/α世代向けなど「個性・遊び心」を出したいBtoC案件と相性が良い。
     - 手描き・アナログ風：生成AIっぽい「整いすぎ」た印象をあえて崩す方向。手仕事感・温かみを出したい案件、暖色寄り・柔らかめの写真トーンと合わせやすい。
     - Bento UI（弁当箱レイアウト）：情報を大小の四角い枠にきれいに整理する方向。サービス紹介・料金プランなど情報量が多い案件、堅実⇔革新の軸で「整った印象」を出したいBtoB案件と相性が良い。
     - ネイチャーハーモニー：木目や石材のような質感、自然由来の落ち着いた配色を組み合わせた方向。手描き・アナログ風に近いが、よりナチュラル・オーガニックな質感を軸にする。暖色寄り・柔らかめの写真トーンや、癒し・信頼感を出したい案件（サロン、士業、地域密着系など）と相性が良い。
     - ハートフェルトピンク：日本流行色協会（JAFCA）が選んだ2026年の色で、温かみのある淡いピンク（例 #F3C6C6 前後）を軸にする方向。手描き・アナログ風やネイチャーハーモニーに近い柔らかさを持ちつつ、より明るく親しみやすい印象を出したい案件（女性向けサービス、美容・生活系、コミュニティ系など）と相性が良い。
     - クラウド ダンサー：色の業界団体パントン社が選んだ2026年の色で、控えめなオフホワイト（例 #F0EEE9 前後）を軸にする方向。「静けさ」「余白」「新しい始まり」を感じさせる、はっきりした色を使わない引き算の配色。士業・医療・ラグジュアリー系など、落ち着き・上質さを出したい案件と相性が良い。
     - アンバー・ヘイズ：色の動向を調査する専門会社WGSNが選んだ2026年の色で、琥珀色がかった温かみのある淡い色合い（例 #D9A873 前後）を軸にする方向。活力とやさしさの両方を感じさせる色として注目されている。ハートフェルトピンクやネイチャーハーモニーに近い温かみを持ちつつ、より活力・華やかさを添えたい案件（飲食・美容・ライフスタイル系など）と相性が良い。
     - タクタイル・リベリオン：AIが作る「ツルツルで整いすぎた」見た目への反動として、あえて手仕事の跡やザラつきを残す方向。2026年の潮流として紹介されている。「手描き・アナログ風」と近い狙い（AIっぽさを崩す）だが、より意識的に「これは人の手で作った」という質感・信頼の記号として押し出したい案件（クラフト系・個人事業主・こだわりの強いBtoC案件など）と相性が良い。
5. **失敗ガード**：リニューアル（Q3 / Q12 / Q42）なら、7章「変えない要素」を**必ず**埋める。Q42が空なら「要確認：消してはいけない目印の特定」と書く。表層的な全面刷新を無検証で推さない。
6. **素材の制約を方向性に反映する**（Q30–33）。絵に描いた餅にしないため、次を確認してから配色・写真の方向を出す。
   - ロゴが画像データ（jpg・png）しかない、またはデータが無い → ロゴの作り直し・トレースが要る可能性を「次のステップ」に明記する
   - 写真が「これから撮影」「用意なし」 → 撮影またはストックフォト購入が前提であることを提案書に書く。手持ち写真前提のトーンを勝手に組まない
   - Q33で今の文章・写真を「変えられない」と回答 → その素材のトーンに寄せた方向を出す。既存素材と衝突する配色・書体を推さない

## Step 3: HTMLに流し込む

`assets/proposal-template.html` の**CSS・レイアウト・構造をそのまま使う**。各セクションの中身だけを入力シートの内容で差し替えて、新しいHTMLとして出力する。

### 3-0: config.json を読み、プレースホルダーを解決する（必須・最初に行う）

`config.json` を読み込み、以下の3つのプレースホルダーを実値に置換してから、案件内容の流し込みに進む。

| プレースホルダー | 参照するキー | 上書き条件 |
|---|---|---|
| `{{BRAND_NAME}}` | `brand.name` | ユーザーが「ブランド名は◯◯」と指定した場合のみ上書き |
| `{{DESIGNER_NAME}}` | `brand.designer` | ユーザーが「担当者名は◯◯」と指定した場合のみ上書き |
| `{{FOOTER_NOTE}}` | `brand.footer_note` | 通常は config の値をそのまま使う |

上書き指示の例（ユーザーがこう言ったら従う）：
- 「担当者名は山田で」→ `{{DESIGNER_NAME}}` を「山田」に
- 「ブランド名はデザイン工房ABCで」→ `{{BRAND_NAME}}` を「デザイン工房ABC」に
- 指示がなければ config.json の値をそのまま使う。**Sakumadesign をデフォルトにしない**。

差し替え時のルール：
- 冒頭の黄色い「記入例です」バナーは、**HTMLの`<div class="sample-banner">`本体と、`<style>`内の`.sample-banner`関連ルール（メディアクエリ内を含む）の両方**を削除する。HTMLだけ消すとCSSが残るので注意。
- 表紙のクライアント名・日付・担当を実値に。
- コンセプト（2章）は、テンプレの`.concept`ブロックを**案の数だけ複製**し、「A案 / B案」とラベルを付ける。
- 制作者メモ（`.note`）は、テンプレの「💡狙い」の趣旨を保ちつつ、その案件に即した内容に書き換える。
  - **初期状態は非表示にしておく**：`<body class="hide-notes">` とし、ボタンを `aria-pressed="false"` ／文言「制作者メモ：非表示」にする。**表示状態のまま渡すと事故になる。**
  - ⚠️ **トグルは「保護」ではない。**ボタンを押せば見え、ソースを表示すれば最初から全文が読める。**クライアントに渡すファイルでは Step 7 の手順でメモを物理削除する。**
  - メモには「クライアントに選択肢として提示しない」「〜様のご判断に委ねる」など、**見られたら気まずい内容を書いてよい**（それが内部メモの価値）。だからこそ物理削除の工程が要る。
- 配色スウォッチのhex・フォントプレビューの書体は、Step 2で決めた候補を反映。フォントを変える場合は`<head>`のGoogle Fonts `<link>`とプレビューの`class`も合わせて変える。
- 未記入項目は、テンプレの`.fill`（斜線の記入枠）スタイルを使って「要ヒアリング」と分かる形で残す。創作で埋めない。

出力先は**案件フォルダの `04_デザイン/`**（例：`04_デザイン/YYYYMMDD_デザイン方向性のご提案_v1.html`）。
これが**内部作業用マスター**になる。クライアント提出用は Step 7 で別途 `_共有用.html` を生成する（メモを物理削除した版）。**マスターを直接クライアントに渡さない。**

## Step 4: 「人が確認すべき箇所」チェックリストを添える

HTML本体とは別に、チャット応答の中で必ず以下の形のチェックリストを出す。自動生成の限界を明示し、デザイナーの判断を促す。

```
## 確認・調整が必要な箇所
- [ ] コンセプト：A/B案のどちらを採るか（または統合）
- [ ] 配色：候補hexは方向性のみ。実際の画面で最終調整を
- [ ] フォント：候補から確定を
- [ ] 参考サイト：URLの採否はデザイナー判断で
- [ ] （リニューアル）変えない要素：Q42の内容で過不足ないか
- [ ] 素材の前提：ロゴ形式・写真の有無・既存文章の変更可否（Q30–33）を方向性に織り込んだか
- [ ] 未記入だった項目：〔具体名〕の追加ヒアリング
```

該当のない項目は省き、未記入だった実際の項目名を列挙する。

## Step 5: 戦略設計書との矛盾を洗い出す

デザイン提案書は単体では完結しない。**多くの場合、先に `web-strategy` で作った「サイト設計のご提案（戦略設計書）」が同じクライアントに渡っている**（または同時に渡す）。2冊を並べて読まれる前提で、食い違いを潰す。

### なぜ必要か

デザイン提案書と戦略設計書は別々のタイミングで作られ、途中でどちらかだけ修正されることが多い。結果、**同じ論点に違うことが書いてある**状態が生まれる。クライアントは並べて読むので、必ず気づかれる。

### 実行方法：機械的に本文を抽出して突き合わせる

目視で読み比べると必ず見落とす。**両方をプレーンテキストに落としてから比較する。**

```python
# 戦略設計書（PDF）
import fitz
d = fitz.open('.../サイト設計のご提案.pdf')
S = "\n".join(d[i].get_text() for i in range(len(d)))

# デザイン提案書（HTML）※制作者メモは内部用なので除外して比較
import re, html
s = open('.../デザイン方向性のご提案_v1.html', encoding='utf-8').read()
s = re.sub(r'<script.*?</script>', '', s, flags=re.S)
s = re.sub(r'<style.*?</style>', '', s, flags=re.S)
body = re.sub(r'<div class="note">.*?</div>', '', s, flags=re.S)
D = html.unescape(re.sub(r'<[^>]+>', ' ', body))
```

### 必ず照合する項目（チェックリスト）

| # | 観点 | よくある食い違い |
|---|---|---|
| 1 | **信頼の根拠** | 戦略書「信頼の根拠は"人"（代表者の経歴）＝唯一の材料」 vs デザイン書「画面の精度そのものを信頼の材料に」→ **正面衝突**。しかも戦略書に「デザインを現代的にするだけでは差はつかない」と書いてあると、デザイン提案の前提ごと否定される |
| 2 | **制作範囲・納品物** | 戦略書の「その他素材」欄にあるのにデザイン書の「今回つくるもの」に無い項目（例：キービジュアル用背景画像）。**ヒアリングシートに無い項目を戦略書が独自に足していないかも確認** |
| 3 | **ターゲットの主従** | 戦略書「B. 士業経由（主ルートとの見立て）」 vs デザイン書「加えて士業」＝付け足し扱い → 優先順位が逆に読める |
| 4 | **宛名** | 「株式会社◯◯ 山田 太郎 様」 vs 「株式会社◯◯ 様」 |
| 5 | **社名・担当者名** | 屋号変更後に片方だけ直っていない。**PDFはフッター全ページ＋PDFプロパティ（author）にも入るので `fitz` の `metadata` まで確認** |
| 6 | **トーンの形容詞** | 戦略書の競合比較表「現代的・硬質」 vs デザイン書「正確・静か・現代的」→ 硬質が消えている |
| 7 | **次のステップの予告** | 戦略書の最終行「次のステップとして色・書体・**イラストのたたき台**をご提案します」 vs 実物にたたき台が無い → 期待値のズレ |
| 8 | **日付** | 作成日と提出日は違ってよいが、意図してそうなっているか確認 |

### 解消の方針

**片方に寄せるのではなく、2冊が補強し合う形にする。** 特に #1（信頼の根拠）は、どちらかを消すのではなく接続する。

```
悪い例：デザイン書から「画面の精度」を削る
良い例：戦略書「唯一の材料」→「最大の材料」に緩め、
        デザイン書に接続の一文を足す：
        「戦略設計書でお伝えした『信頼の根拠を人に置く』方針は変わりません。
          ここでご提案するのは、それを画面の側から支える考え方です。
          経歴という文章は読んで初めて効きますが、読む前の一瞬で
          『きちんとした機関だ』と感じてもらえなければ読んでもらえません。」
→「人 か 画面か」の対立が「人を読んでもらうために画面が入口を作る」の順接になる
```

### 修正時の鉄則：全ファイルを同時に、一致しなければ保存しない

戦略設計書は通常 **3ファイル**（内部MD／PDF生成スクリプト／HTMLプレビュー）に分散している。デザイン提案書と合わせて **4ファイル**を同時に直す。**1つでも文字列が一致しなければ、どのファイルも保存しない**方式にすること。片側だけ直った状態が最悪。

```python
allok = True; newtext = {}
for path, edits in targets.items():
    s = open(path, encoding="utf-8").read()
    for name, old, new in edits:
        ok = old in s
        if ok: s = s.replace(old, new, 1)
        else:  allok = False
        print(("OK  " if ok else "NG  ") + name)
    newtext[path] = s
if allok:
    for path, s in newtext.items(): open(path, "w", encoding="utf-8").write(s)
else:
    print("一致しない箇所があるため、どのファイルも保存していません")
```

PDF生成スクリプトを直したら **PDFを再ビルドし、抽出テキストで再照合する**まで完了としない。

### あわせて確認する「クライアントが知らない経緯」

矛盾チェックと同時に、**先方が見ていない検討過程を書いていないか**も洗う。社内では2案・3案と検討していても、クライアントが見たのは最終形だけ。「変更しました」「当初は〜でしたが」と書くと、**存在しない前回版を前提にした文章**になる。

```python
pats = ["変更しま","当初","もともと","元々","やめ","取り下げ","前回","以前","見直し","改めま"]
```

本文（制作者メモを除く）に対して実行し、ヒットしたら**決定した内容だけを述べる形**に書き換える。

```
❌ 地の色を純白（#FFFFFF）から明るいグレーに変更しました
✅ 地の色は、純白（#FFFFFF）ではなく明るいグレーにしています
```

同じ理由で、**「当初案／採用案」という対比表も使わない**。「A形式にした場合／B形式（ご提案する設計）」のような、決定が覆ったのではなく**2つを比較しただけ**に見える形にする。

### 「要確認」の記入枠を残したまま出さない

テンプレの `.fill`（斜線の記入枠）や「要確認：」は**制作途中の印**。提出前に必ず全件を解消する。

- **こちらで判断できるもの** → 根拠を添えて確定文に置き換える（例：「サイトを見た方には『信頼できる』と感じていただくことを目指します。0章の目的とトーン診断の全軸が『2』であることから、この一点に絞りました」）
- **色の近似値など、性質上あとで詰めるもの** → 「要確認」ではなく**通常の設計フロー**として書く（例：「方向性を示す候補値であり、正確な値はカンプ制作時に確定する」）

提出前に `grep -c "要確認"` が **0** であることを確認する。

### 発言の出所を偽らない

提案書で「〜とお伝えしたとおり」「ご指定いただいた」と書くときは、**本当にクライアント発か**を確認する。

- 参考サイトを選んだのが**自社側**なら「お示しいただいた」は誤り →「参考にしている」
- 根拠がヒアリングシートにも議事録にも無い記述（例：「営業担当はなく」）は**推測を断定で書いている** → 削除するか、根拠のある表現に直す
- クライアントの推測混じりの発言（「〜じゃないかと思う」）を引くときは「**〜との見立て**」と添える。断定に格上げしない

疑わしいときは案件フォルダを横断検索し、**議事録・ヒアリングシート・文字起こしのどれに載っているか**まで確かめる。

## Step 6: PDFがきれいに収まるようにする

クライアントは「Webページ版」と「PDF版」の両方を欲しがることが多い。**テンプレの`@media print`は部品単位で改ページ制御する設計になっている**（2026-08-20修正済み）。

### 直した内容と、その理由

```css
/* ❌ 修正前：章まるごとを1ページに収めようとする
   → 章が1ページに収まらない場合に強制的に途中で割られ、
     カラースウォッチやカードが真っ二つになる。
     かつ短い章は丸ごと次ページに送られ、巨大な余白ができる */
.section{break-inside:avoid;}

/* ✅ 修正後：部品単位で保護する */
.rail{break-after:avoid;}
.body h2, .body h3{break-after:avoid; break-inside:avoid;}
.concept, .sw, .frow, .ref, .kc, .swatches, .fonts,
.callout, .scale, table, tr{break-inside:avoid;}
.lead{break-after:avoid;}
```

**考え方**：文章の段落は自然に流れてよい。守るべきは「視覚的に1つのまとまりとして見えるもの」＝カード・スウォッチ・表・見出しと直後の本文の結合。

### 検証方法（目視で判断しない）

Chromeのヘッドレスで実際にPDF化し、全ページを画像にして確認する。

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --no-margins \
  --print-to-pdf="出力.pdf" --print-to-pdf-no-header \
  "file:///絶対パス/提案書.html"
```

```python
import fitz
d = fitz.open('出力.pdf'); print('pages:', len(d))
for i in range(len(d)):
    d[i].get_pixmap(dpi=100).save(f'chk_p{i+1}.png')
```

生成した画像を1枚ずつ Read して、**カード・スウォッチ・表が途中で切れていないか**を実際に見る。修正前後でページ数を比較すると効果が分かる（実績：13→12ページ、切れ箇所ゼロ）。

### ユーザーに必ず伝えること

ブラウザの印刷ダイアログは**日付・URL・ページ番号を自動で入れる**。これはCSSでは消せない。

> 印刷ダイアログの「**ヘッダーとフッター**」のチェックを**オフ**にしてから保存してください。

## Step 7: Web公開前の準備（Netlify）

「スマホで見せたい」「リンクで共有したい」と言われたときの手順。

### まず選択肢を正しく説明する

| 方法 | 判定 | 理由 |
|---|---|---|
| **GitHub Pages** | ⚠️ 非推奨 | 無料プランでは**閲覧制限をかけられず全世界に公開**される。クライアント社名・担当者名・**競合他社の実名評価**が入った資料には不適 |
| **Googleドライブに素のHTML** | ❌ 機能しない | ドライブのプレビューはHTMLを**ソースコードとして表示**する。デザインが再現されない |
| **Googleドライブ＋PDF** | ○ 可 | 確実だがPDFなので読みづらいことがある |
| **Netlify（無料）** | ◎ 推奨 | ランダムな長いURLで発行され、検索にも出ない。後から更新・削除も可能 |

### 公開用ファイルの作り方

**重要：制作者メモの「非表示トグル」は保護になっていない。** ボタンを1回押せば見え、そもそも「ページのソースを表示」すれば最初から全文が読める。**メモ自体を物理的に除去した別ファイルを作る。**

```python
import re
s = open(src, encoding="utf-8").read()

# 1) .note ブロックを物理削除（件数をassertで固定し、想定外の削除を防ぐ）
s2, n = re.subn(r'\n?\s*<div class="note">.*?</div>\n?', '\n', s, flags=re.S)
assert n == 9, n

# 2) トグルボタンを削除
s3, n = re.subn(r'\s*<button class="tbtn" id="noteToggle"[^>]*>[^<]*</button>\n', '\n', s2)
assert n == 1

# 3) トグルのJSを削除（要素が無くなるためエラー防止）
s4, n = re.subn(r"<script>\s*\(function\(\)\{.*?noteToggle.*?\}\)\(\);\s*</script>", "", s3, flags=re.S)
assert n == 1

# 4) body の hide-notes を戻す
s5 = s4.replace('<body class="hide-notes">', '<body>')

# 5) 検索避けを付与
s6, n = re.subn(r'(<title>[^<]*</title>)',
                r'\1\n<meta name="robots" content="noindex, nofollow">', s5, count=1)
assert n == 1
```

**戦略設計書のHTMLプレビューにも内部表示が残っていることがある**（例：`<span class="conf-badge">プレビュー用（社内確認）...</span>`、`<title>`の「（プレビュー）」表記）。これも共有版からは除く。

### 検証（公開前に必ず）

```python
danger = ['先方のご判断に委ねる','クライアントに選択肢として提示する','取り下げ',
          '目視で読み取った近似値','手戻りが大きい','必ず口頭で','社内確認']
for d in danger: print(f'{s.count(d)}件  {d}')   # すべて0件であること
```

### 配置構成

複数の資料を1つのURLから見せるため、入口ページを作る。

```

├── index.html           ← 入口（各資料へのリンクカード）

```

`index.html` にも `noindex` を入れる。3ファイルすべてに入れること。

### ユーザーへの案内（Netlify）

1. [app.netlify.com/signup](https://app.netlify.com/signup) で無料登録（**パスワード入力を伴うので必ず本人が行う。代行しない**）
2. 「Add new site」→「Deploy manually」
3. **フォルダごと**ドラッグ＆ドロップ（個別ファイルではない）
4. ⚠️ **発行直後は「Private」になっている。** そのままだとNetlifyにログインしていないクライアントは開けず、"This site is private" と表示される。**「Make public」を押してもらう**
5. 公開後、こちらで実際にURLへアクセスし、以下を検証する
   - 入口・各資料が正しく表示されるか
   - `document.querySelector('.note')` が `null` か（メモ残存ゼロ）
   - `meta[name="robots"]` が `noindex, nofollow` か

### 更新時の注意

**Netlifyは自動更新されない。** HTMLを直したら、アップロード用フォルダにコピーし直し、**再度ドラッグ＆ドロップが必要**（URLは変わらない）。この点をユーザーに必ず伝える。

### セキュリティ上の但し書き

Netlify無料プランではパスワードをかけられない。URLを知っていれば誰でも見られる。送付時に一言添えるよう案内する。
